# Выявление секретов в тексте

## Определение

Поиск в тексте **секретов**: API-ключей, токенов доступа, паролей, приватных ключей, seed-фраз кошельков. Обнаружение по **известным префиксам** (`sk-`, `AKIA`, `ghp_`), **регулярным выражениям** и **высокой энтропии** (случайность символов).

## Как это работает пошагово

1. Текст (промпт, ответ, аргумент инструмента) сканируется сканером.
2. **Префиксный детектор**: совпадение с каталогом форматов (OpenAI, AWS, GitHub, JWT…).
3. **Энтропийный детектор**: длинные фрагменты с аномально высокой случайностью — кандидат в секрет.
4. **Контрольные суммы** (Luhn, WIF для криптоключей) — подтверждение формата.
5. При совпадении — **блок**, **маскирование** или **алерт**; в Pipelock проверка идёт **до DNS-запроса**, чтобы секрет не ушёл даже на резолвинг домена.

## От чего защищает

- Случайное вставление ключа разработчиком в промпт.
- Утечка секрета в **ответе** модели пользователю или в логи.
- Ключи в markdown навыков (пересечение с цепочкой поставки).
- OWASP LLM02, LLM06 (частично).

## От чего НЕ защищает

- **Медленная утечка**: секрет дробится на части в многих запросах (нужен слой энтропии Pipelock).
- Легитимная передача секрета **разрешённым** инструментом.
- Секрет в **зашифрованном** виде без распознаваемой сигнатуры.
- Секрет только в бинарном файле без текстового слоя.

## Алгоритмы и механизмы (подробно)

### Каталог префиксов

Аналог TruffleHog / Gitleaks: для каждого провайдера — префикс + длина + алфавит символов. Пример: OpenAI `sk-proj-...`, AWS `AKIA...`.

### Энтропия Шеннона

Если подстрока выглядит как случайный набор символов (высокая энтропия), она помечается даже без известного префикса. Pipelock анализирует **путь URL** и **поддомены** против **медленной утечки**.

### Предикаты в Invariant

В правилах трасс можно вызвать встроенную проверку `secrets()` на любом текстовом поле события.

### Технические детали внедрения

- **Предварительное декодирование.** Перед поиском секретов часто выполняют URL-decode, Base64/hex-попытки, склейку разорванных строк и нормализацию разделителей. Иначе утечка в query-параметре, markdown-коде или обфусцированном фрагменте не совпадёт с сигнатурой.
- **Смешанный скоринг.** Один только regex даёт много FP, а одна энтропия ловит случайные хеши. Поэтому продакшен-сканеры комбинируют префикс/формат, длину, алфавит, checksum и энтропийный порог по окну фиксированного размера.
- **Проверка валидности формата.** Для JWT можно проверить структуру `header.payload.signature`, для AWS ключей - характерный префикс и длину, для BIP-39 - словарь и checksum-фразу. Такая валидация сильно сокращает шум.
- **Накопление частичных утечек.** Опасный секрет может вытекать по кускам в нескольких сообщениях или доменных метках. Поэтому полезно хранить sliding window по сессии и агрегировать подозрительные фрагменты в единый verdict.
- **Сканирование не только тела.** Проверять нужно URL, query string, заголовки, имена файлов, поддомены и аргументы инструментов. Многие реальные утечки уходят не в «тексте ответа», а в служебных полях запроса.
- **Подавление ложных совпадений.** UUID, commit hash, тестовые токены и публичные ключи часто выглядят «случайными». Для них держат allowlist-классы и контекстные исключения, иначе операторский шум быстро обесценивает систему.
