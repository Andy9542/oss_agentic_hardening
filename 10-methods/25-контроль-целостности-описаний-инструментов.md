# Контроль целостности описаний инструментов по контрольной сумме

## Определение

**Rug-pull** — атака, когда MCP-сервер после «чистой» установки **меняет описания** инструментов в `tools/list`, подсовывая скрытые инструкции. Защита: при первом контакте сохранить **SHA-256** хеш описаний; при каждом последующем — сравнение с эталоном.

## Как это работает пошагово

1. **Установка / первый запуск** — сервер отдаёт список tools → вычисляется хеш → сохраняется baseline.
2. **Каждый запрос** `tools/list` или ответ MCP → новый хеш.
3. **Несовпадение** → алерт, блок сессии, требование переустановки.
4. Легитимное обновление tools → процедура **пересоздания baseline** с подписью DevOps.

## От чего защищает

- Отравление описания **после** аудита на установке.
- Подмена метаданных без смены имени инструмента.

## От чего НЕ защищает

- Вредоносное описание **уже в первом** baseline.
- Изменение **поведения** сервера без смены текста описания.
- Атаки в **результатах** tool, не в descriptions.

### Технические детали внедрения

- **Канонизация перед хешированием.** Перед вычислением SHA-256 описание, schema и список инструментов нужно сериализовать детерминированно: стабильный порядок полей, нормализованные пробелы, предсказуемая кодировка, одинаковое представление чисел и булевых значений.
- **Гранулярность baseline.** Практично хранить как хеш на каждый инструмент, так и общий хеш всего `tools/list`. Первый помогает локализовать изменение, второй быстро выявляет несоответствие снимка целиком.
- **Доверенное хранилище baseline.** Контрольная сумма бесполезна, если атакующий может переписать и артефакт, и baseline. Поэтому эталон лучше держать в подписанном репозитории политик, отдельном KV-хранилище или в CI-артефакте с ограниченной записью.
- **Подпись и ротация ключей.** Если baseline подписывается, нужен понятный жизненный цикл ключей: генерация, хранение, ротация, отзыв и проверка старых подписи в истории. Это особенно важно для длинноживущих инвентарей MCP-серверов.
- **Легитимные изменения.** Обновление описания инструмента должно проходить через review: показать diff schema/description, кто инициировал смену и когда baseline был перевыпущен. Иначе rug-pull защита будет конфликтовать с нормальной эволюцией сервера.
- **Проверка значимых полей.** Помимо описания, стоит контролировать имена инструментов, типы аргументов, значения `required`, `enum`, поддерживаемые URL и другие метаданные, которые напрямую меняют поверхность атаки.
