# Изоляция агента в микровиртуальных машинах и контейнерах

## Определение

Код и среда агента выполняются в **изолированной** виртуальной машине (Firecracker) или контейнере с отдельным сетевым пространством имён. После сессии среда **уничтожается** — не остаётся персистентного вредоноса.

## Как это работает пошагово

1. **create** — поднять microVM (отдельное ядро Linux) или контейнер.
2. **execute** — передать код/команды агента внутрь.
3. **ограничить egress** — только whitelist доменов или без сети.
4. **read** результат из изолированной среды.
5. **destroy** — удалить ВМ; секреты хоста недоступны при корректной конфигурации.

E2B: оркестратор → Firecracker VMM → демон envd внутри гостя; холодный старт ~125 мс (с E2B Cloud).

## От чего защищает

- Компрометация **хоста** через сгенерированный код.
- Lateral movement к соседним процессам.
- Персистентность после атаки.

## От чего НЕ защищает

- Легитимный перевод денег через **разрешённый** банковский API внутри песочницы.
- Prompt injection → вредное **разрешённое** действие.
- CVE escape из hypervisor (редко, критично).

### Технические детали внедрения

- **Границы изоляции.** Контейнеры полагаются на общее ядро хоста, namespaces, cgroups и seccomp, тогда как microVM добавляет отдельное виртуализованное ядро и сильнее режет поверхность побега. Выбор зависит от цены старта, плотности размещения и допустимого риска.
- **Файловая система и жизненный цикл.** Безопасная песочница обычно использует ephemeral overlay FS, read-only base image, отдельный writable layer и гарантированное уничтожение слоя после завершения сессии. Это уменьшает persistence после компрометации.
- **Секреты внутри гостя.** Даже в изолированной среде нельзя просто прокидывать все ключи как env vars. Лучше выдавать короткоживущие токены, scoped credentials и отдельные mounts только для нужных инструментов.
- **Сеть и обходные пути.** Изоляция должна включать отдельный network namespace, жёсткие egress-правила, запрет host networking и контроль прокси-маршрутов. Иначе агент может обойти внешние guardrails прямым сокетом.
- **Монтажи и флаги безопасности.** `noexec`, `nosuid`, `nodev`, read-only mounts и ограниченный список Linux capabilities заметно сужают последствия RCE внутри песочницы.
- **Форензика при инциденте.** Перед уничтожением среды полезно уметь сохранить snapshot, stdout/stderr, список процессов и сетевые соединения, иначе расследование атаки на ephemeral sandbox почти невозможно.
