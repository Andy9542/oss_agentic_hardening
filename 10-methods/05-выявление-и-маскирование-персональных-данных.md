# Выявление и маскирование персональных данных

## Определение

Автоматический поиск в тексте **персональных данных** (ПДн): имена, адреса электронной почты, телефоны, номера документов, банковские реквизиты и т.п. Найденные фрагменты **заменяются** на безопасные плейсхолдеры (`<EMAIL_1>`, `<PERSON_2>`) **до** отправки текста во внешнюю языковую модель или **после** генерации ответа — перед показом пользователю.

Комбинирует **регулярные выражения**, **распознавание именованных сущностей (NER)** и **словари типов** данных.

## Как это работает пошагово

1. **Сканирование** — текст проходит через цепочку детекторов (regex → NER → словари).
2. **Разметка** — каждому найденному фрагменту присваивается тип (EMAIL, PHONE, PERSON…) и позиция в строке.
3. **Замена** — оригинал подставляется в **таблицу соответствий** (если нужна обратная подстановка), на месте остаётся токен-заглушка.
4. **Передача в модель** — модель видит только маски; не может «случайно» процитировать реальный email в логах провайдера.
5. **Обратная подстановка (опционально)** — после ответа модели плейсхолдеры заменяются обратно по таблице (режим deanonymize в llm-guard).

```
Исходный текст → [детекторы] → маскированный текст → LLM → ответ с масками → [deanonymize?] → ответ пользователю
```

## От чего защищает

- **Случайная утечка** ПДн в промпте или ответе в сторону API модели и в логи.
- **Непреднамеренное** включение чувствительных полей в контекст RAG.
- Частично **OWASP LLM02** (раскрытие чувствительной информации).
- **Регуляторика**: GDPR, HIPAA — как **технический** слой (не заменяет организационные меры).

## От чего НЕ защищает

- **Утечка через действие**: агент легитимно вызывает `send_email(тело=...)` с ПДн — маскирование в промпте не мешает инструменту.
- **Косвенная идентификация**: «мужчина 47 лет из Казани, работает в X» без имени — NER может не сработать, человек всё равно узнаваем.
- **Компрометация таблицы deanonymize** — атакующий восстанавливает все маски.
- **Опасный tool_call** — маскирование не блокирует вызов.

## Алгоритмы и механизмы (подробно)

### Регулярные выражения и контрольные суммы

- **Email**: шаблон `local@domain`.
- **Телефон**: маски под страны.
- **Банковские карты**: regex + алгоритм **Луна** (Luhn) — отсекает случайные 16 цифр.
- **IBAN**: проверка **mod-97**.
- Pipelock DLP использует 48+ шаблонов и несколько контрольных сумм.

Плюс: быстро, детерминированно. Минус: нестандартные форматы и опечатки.

### NER (распознавание именованных сущностей)

Модель или правила выделяют **PERSON**, **LOCATION**, **ORG** в свободном тексте. Microsoft **Presidio** — эталонный open-source стек «анализатор + анонимизатор».

Плюс: имена без шаблона. Минус: ошибки на редких языках, доменном жаргоне, коротких текстах.

### Словари типов (agent-airlock)

12+ категорий, включая региональные идентификаторы (например, индийские). Жёсткий перечень — предсказуемое поведение без GPU.

### Обратная подстановка (deanonymize)

llm-guard хранит соответствие `<EMAIL_1>` → `user@corp.com` в защищённом хранилище, чтобы ответ модели с плейсхолдерами снова стал читаемым. **Новая поверхность атаки**: кто владеет vault — видит все ПДн сессии.

### Технические детали внедрения

- **Каскад детекторов.** Обычно сначала работают точные regex и checksum-проверки для e-mail, телефонов, ИНН, карт и т.п., затем NER-модели для сущностей типа PERSON или LOCATION. После этого движок разрешает перекрытия: например, длинная строка может одновременно походить на номер документа и произвольный идентификатор.
- **Детерминированные плейсхолдеры.** Для последующей деанонимизации или сохранения связности текста значения заменяют не просто на `[MASK]`, а на стабильные маркеры вида `<EMAIL_03>`. Тогда повторяющийся адрес остаётся тем же маркером в пределах сессии.
- **Региональные форматы.** ПДн сильно зависят от юрисдикции: паспортные шаблоны, национальные идентификаторы, почтовые индексы и телефоны отличаются по странам. Реально работающая система хранит профили детекторов по региону или tenant'у.
- **Обратная подстановка.** Если маскированные данные позже нужны легитимному инструменту, их нельзя держать в открытом виде в памяти агента. Обычно используют отдельное хранилище с TTL, шифрованием и ключом с ограниченным сроком жизни, а в текст передают только токены-заместители.
- **Маскирование до журналирования.** PII нужно убирать до логов, трассировок, prompt replay и экспортов в observability-стек, иначе защита на основном ответе не спасает от утечки через побочные каналы.
- **Частичная деидентификация.** Для некоторых процессов полезнее сохранять часть структуры, например последние 4 цифры карты или домен e-mail. Это позволяет дебажить и коррелировать события, не раскрывая полный секрет.

## Оценка эффективности

**Уровень:** средний

**Обоснование:** На **структурированных** ПДн (email, карты с checksum) работает надёжно; широко внедрён в NeMo, llm-guard, корпоративный DLP. **Не решает** агентную утечку через инструменты и сеть.

## Оценка прочности

**Уровень:** средний

**Обходы:**

- Нестандартный формат идентификатора (пробелы внутри номера, разбивка на части).
- Частичное маскирование — в контексте остаётся достаточно для реидентификации.
- Атака на vault обратной подстановки.
- Пропуск NER на редком языке при многоязычном агенте.
