# Правила против инъекций в аргументах инструментов

## Определение

В **строках аргументов** вызова инструмента ищутся **сигнатуры** классических инъекций: SQL (`DROP`, `DELETE`, `'; --`), обход каталога (`../../etc/passwd`), метасимволы shell (`|`, `;`, `` ` ``), обфусцированные команды.

## Как это работает пошагово

1. **Извлечение** — рекурсивный обход всех строк в JSON аргументов (вложенные объекты, массивы).
2. **Нормализация** — раскодирование URL, unicode (в продвинутых системах).
3. **Сопоставление** с наборами правил по категориям: SQL / path / shell.
4. **Вердикт** — блок до исполнения; в Aegis — стадия 2 из 3 перед YAML-политикой.

Aegis заявляет: 48/48 тестовых атак заблокированы, ~1,2% ложных срабатываний на 500 легитимных вызовов, медиана ~8,3 мс.

## От чего защищает

- SQL-инъекция через DB-tool агента.
- Чтение `/etc/passwd` через path traversal.
- `rm -rf /`, `curl | bash`, подстановка через переменные shell.
- Шаблоны «игнорируй инструкции» **внутри аргумента**, не только в чате.

## От чего НЕ защищает

- Деструктивный API без «подозрительных» строк в args.
- Новая обфускация до обновления правил.
- Атака только в промпте, не дошедшая до args.

## Алгоритмы (подробно)

| Класс | Примеры правил |
|-------|----------------|
| SQL | Ключевые слова DDL/DML, комментарии `--`, `UNION SELECT` |
| Path | `..`, кодированный `%2e%2e`, чувствительные пути `.env`, `.ssh` |
| Shell | 17 правил Pipelock + детекция обфускации через `$()`, backticks |
| Префиксы | Запрет `delete_`, `drop_`, `rm` в именах инструментов (agent-airlock) |

### Технические детали внедрения

- **Рекурсивный обход аргументов.** Проверять нужно не только верхнеуровневые строки, но и все вложенные поля JSON, элементы массивов, env-переменные и шаблоны внутри строк. В отчёте полезно сохранять путь к полю: `payload.commands[2].path`.
- **Нормализация входа.** Перед матчингом строку очищают от экранирования, двойных пробелов, shell-обфускации, mixed-quote конструкций, URL-encoding и Unicode-трюков. Иначе простые правила видят безопасную форму, а интерпретатор - опасную.
- **Grammar-aware анализ.** Для SQL и shell надёжнее проверять токены и AST, а не только regex. Например, можно отдельно выявлять операторы `UNION`, `COPY TO PROGRAM`, пайпы, redirection, command substitution и переменные окружения.
- **Политики по типу поля.** Поле `path` проверяют по allowlist корня, `query` - на инъекции и размер, `command` - по набору разрешённых бинарников и флагов, `url` - по доменам и протоколам. Один общий regex на всё обычно либо дырявый, либо шумный.
- **Метрики по классам атак.** SQL, shell, path traversal и command injection имеют разный профиль FP/FN, поэтому полезно считать статистику отдельно и откатывать правила по классам, а не весь движок целиком.
- **Поведение при совпадении.** Критичные паттерны должны вести к hard block, менее уверенные - к эскалации или sandbox-only режиму. Это помогает не ломать полезные сценарии при первой же неоднозначности.
