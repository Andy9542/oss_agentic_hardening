## Как читать этот документ

У каждого инструмента четыре блока:

1. **Детекторы** — что именно ищет, на каком этапе, чем проверяет.
2. **Архитектура** — куда встаёт в цепочке «пользователь → агент → инструменты», как подключается.
3. **Тип методов** — жёсткие правила, модели, смешанный подход.
4. **Внешние сервисы** — что требует облака, что работает локально.

**Важно:** не все 20 — защита в продакшене. AgentDojo, garak, promptfoo — **оценка и красное тестирование**, а не барьер в рантайме.

# 1. agent-governance-toolkit (AGT)

### Детекторы (подробно)

AGT — не один детектор, а **набор модулей**, каждый закрывает свой класс рисков:

| Модуль | Что обнаруживает / блокирует |
|--------|------------------------------|
| **Agent OS — движок политик** | Вызов инструмента, доступ к ресурсу, межагентное сообщение. Решение: разрешить / запретить / эскалировать. Поддержка YAML, JSON, OPA Rego, Cedar. |
| **GovernancePolicy** | Запрещённые шаблоны, лимиты токенов, перехват по имени инструмента и аргументам. |
| **Capability Model** | Модель «наименьших привилегий»: агенту выдаётся только набор допустимых действий. |
| **AgentMesh** | Криптографическая идентичность (Ed25519, DID), доверие 0–1000, пять уровней поведения. |
| **Agent SRE** | Автовыключатели при росте ошибок, SLO, аварийное завершение агента. |
| **Agent Compliance** | Соответствие OWASP ASI (все 10), HIPAA, SOC2, EU AI Act — сбор доказательств. |
| **Agent Runtime** | Кольца исполнения (как уровни привилегий в ОС), саги для многошаговых операций. |
| **mcp-scan CLI** | Отравление описаний MCP, rug-pull (смена описания после установки). |
| **Agent Marketplace** | Подпись и верификация плагинов. |

**Чего нет:** семантического анализа «это инъекция в письме» на уровне текста — AGT силён на **действиях**, не на смысле фразы.

### Архитектура встраивания

Три режима развёртывания:

1. **Внутри процесса** — middleware в LangChain, CrewAI, AutoGen, Semantic Kernel, OpenAI Agents SDK. Каждый `tool_call` проходит через `StatelessKernel` / `ToolCallInterceptor` **до** выполнения.
2. **Боковой контейнер (sidecar)** — отдельный сервис рядом с агентом в Kubernetes / Azure Container Apps.
3. **Отдельный сервис политик** — централизованные правила для парка агентов.

Метафора из документации: **«ядро для агентов»** — как POSIX-ядро для процессов. Граница доверия — интерпретатор Python (как у большинства агентных фреймворков). Для высокой безопасности рекомендуют: агент в отдельном контейнере + AGT внутри.

### Детерминизм vs интеллект

| Слой | Тип |
|------|-----|
| Разрешение/запрет действия | **Строго детерминированный** — правила, не «мнение» модели |
| Trust scoring (0–1000) | Эвристика по поведению — **не формальная гарантия** |
| Генерация политик | Может подключаться внешний корпус правил; сами правила — декларативные |

### Внешние сервисы

- **OPA** — опционально, как backend политик.
- **Azure Monitor / внешнее хранилище аудита** — для неизменяемого журнала.
- **Внешний PKI** — для жизненного цикла сертификатов.
- **Без облака:** ядро политик, адаптеры, локальный аудит (SQLite Flight Recorder) работают автономно.

# 2. Pipelock

### Детекторы (подробно)

Один бинарник, **11-слойный конвейер** на каждый запрос (HTTP, WebSocket, MCP, A2A):

| Слой | Назначение |
|------|------------|
| Схема URL | Только http/https, блок опасных схем |
| CRLF-инъекция | Подмена заголовков в URL/теле |
| Обход каталогов | `../`, чувствительные пути |
| Чёрный список доменов | Запрет известных вредоносных/утечных хостов |
| DLP | 48 шаблонов ключей, токенов, финансовых идентификаторов, криптоключей; 4 контрольные суммы (Luhn, mod-97, ABA, WIF) |
| Энтропия пути/поддомена | Медленная утечка, разбиение секрета на части |
| SSRF + DNS rebinding | Запросы во внутреннюю сеть |
| Лимиты | По домену, длина URL, бюджет данных |
| Сканирование ответов | 25+ шаблонов инъекций, 6 проходов нормализации (нулевая ширина, омоглифы, leetspeak) |
| MCP: вход | DLP и инъекции в аргументах инструментов |
| MCP: выход | Инъекции в результатах, отравление `tools/list`, rug-pull по SHA256 |
| Оболочка | 17 правил опасных команд, обфускация shell |
| BIP-39 | Фразы восстановления кошельков |

**Принцип:** DLP **до** DNS — секрет не уходит в сеть даже на резолвинг. Режим **fail-closed**: таймаут, ошибка разбора, сжатый нечитаемый контент → блок.

### Архитектура

**Разделение возможностей:**
- агент хранит секреты, но **не имеет** прямого сетевого доступа;
- Pipelock имеет сеть, но **не хранит** секреты агента.

Встраивание:
- HTTP: агент ходит только на `http://pipelock/proxy?url=...`;
- MCP: `pipelock mcp proxy -- npx server` оборачивает stdio/HTTP/WebSocket;
- A2A: прокси протокола агент–агент.

Обязательно: **сетевая изоляция** агента (Docker `internal: true`, NetworkPolicy, iptables), иначе агент обойдёт прокси сырыми сокетами.

### Детерминизм vs интеллект

**Полностью детерминированный.** Нет нейросетей. Только правила, шаблоны, энтропия, хеши. Плюс — предсказуемость и аудит; минус — обход новыми кодировками до обновления правил.

### Внешние сервисы

**Не требует облака.** Локальный Go-бинарник ~20 МБ. Криптографические квитанции аудита (Ed25519) — локально. CycloneDX SBOM — локально.

# 3. Progent

### Детекторы

Progent не «ищет вирусы в тексте» — он **проверяет каждый вызов инструмента** против символьной политики:

| Механизм | Детали |
|----------|--------|
| Правила по имени инструмента | `send_email` разрешён только если `to` из белого списка |
| Правила по аргументам | Ограничения на поля JSON (шаблоны, перечисления, диапазоны) |
| SMT-решатель (Z3) | Каждое обновление политики: **сужение** (применяется автоматически) или **расширение** (только с одобрением) |
| Монотонное ограничение | Пространство допустимых действий **не растёт** без явного согласия |
| Генератор политик (LLM) | Из задачи пользователя строится начальная политика; при появлении новых данных — уточнение |

**Результаты из статьи:** ASR с ~40% до ~1% (AgentDojo), с ~70% до ~4% (ASB).

### Архитектура

Встраивается **в цикл агента** между решением модели и исполнением инструмента:

```
Модель → «хочу вызвать tool(X, args)» → Progent.check() → исполнение / отказ / запрос одобрения
```

Не меняет внутренности агента — только обёртка вокруг вызовов. Интеграции: AgentDojo, ASB, EhrAgent. Язык политик — доменно-специфичный (модульный фреймворк).

### Детерминизм vs интеллект

| Часть | Тип |
|-------|-----|
| Проверка вызова | **Детерминированная** |
| SMT-сужение/расширение | **Формально детерминированная** |
| Написание и обновление политики | **Интеллектуальная** (LLM) — качество политики зависит от модели |

### Внешние сервисы

- **LLM API** — для генерации политик (обязательно для автоматического режима).
- **Z3/SMT** — локально.
- Пока **исследовательский** уровень зрелости, не промышленный стандарт.

# 4. snyk/agent-scan

### Детекторы

Сканер **цепочки поставки** агентов (наследник mcp-scan от Invariant):

| Код / категория | Что ищет |
|-----------------|----------|
| E001 | Инъекция в промпт, отравление инструмента |
| E002 | Затенение инструмента (tool shadowing) |
| E004 | Инъекция в навыках (skills) |
| E006 | Вредоносная нагрузка в навыках |
| W007, W008 | Обращение с учётными данными, захардкоженные секреты |
| W011 | Недоверенный контент |
| Toxic flows | Опасные **цепочки** инструментов (чтение файлов + внешняя отправка) |
| Rug-pull | Смена описания после установки |
| Malware patterns | curl\|bash, бэкдоры, отключение защиты |

**Процесс:** автообнаружение конфигов Claude/Cursor/Windsurf/Gemini CLI → запуск MCP-серверов → чтение `tools/list`, промптов, ресурсов → локальные проверки + **облачный API Snyk**.

### Архитектура

**Не в рантайме.** Только CI/CD или ручной запуск на машине разработчика:

```
snyk-agent-scan scan [CONFIG]  →  отчёт с кодами проблем
```

Для stdio-MCP — интерактивное согласие перед запуском каждого сервера; в CI — флаг `--dangerously-run-mcp-servers` только в доверенной среде.

### Детерминизм vs интеллект

| Слой | Тип |
|------|-----|
| Локальные проверки | Детерминированные шаблоны |
| Облачный Agent Scan API | **Семантический / ML-анализ** описаний и навыков |
| Toxic flows | Граф зависимостей инструментов — логический анализ |

### Внешние сервисы

- **Snyk API обязателен** для полного анализа (`SNYK_TOKEN`).
- Данные (имена инструментов, описания, навыки) **передаются в Snyk** — нужно согласие с условиями использования.
- Интеграция с Snyk Evo / MDM (CrowdStrike) — для фонового сканирования парка машин.

# 5. agentgateway

### Детекторы

Это **шлюз и контроль доступа**, не антивирус текста:

| Механизм | Назначение |
|----------|------------|
| JWT / OAuth / OIDC | Кто вызывает MCP/A2A |
| MCP Authorization (CEL) | Какие инструменты доступны по claims токена |
| RBAC | Роли → набор tools/resources/prompts |
| Rate limiting, TLS, CORS | Защита от злоупотребления и перехвата |
| Tool poisoning (базовый) | Контроль поверхностей MCP |
| OpenTelemetry | Трассировка, метрики, журнал решений allow/deny |

Пример правила CEL: `jwt.sub == "test-user" && mcp.tool.name == "add"`.

### Архитектура

**Обратный прокси** для MCP и A2A под Linux Foundation:

```
Агент → agentgateway:3000 → [политики] → backend MCP-серверы
```

Особенности MCP:
- мультиплексирование: один `list tools` → fan-out на несколько серверов;
- маршрутизация SSE-событий от сервера к клиентской сессии;
- единая точка аутентификации для «зоопарка» MCP.

Развёртывание: standalone proxy или Kubernetes Gateway API. Один шлюз и для обычных API, и для LLM/MCP — без отдельного «ИИ-шлюза».

### Детерминизм vs интеллект

**Почти полностью детерминированный.** Решения по токену и выражениям CEL — воспроизводимы. Нет классификатора инъекций в теле письма.

### Внешние сервисы

- **Провайдер идентичности** (OAuth/OIDC) — обычно корпоративный IdP.
- **Внешний authz** (OPA) — опционально.
- Сам шлюз — self-hosted, Rust, высокая производительность.

# 6. PurpleLlama / LlamaFirewall

### Детекторы

Три основных сканера + пользовательские regex:

| Сканер | Вход | Метод | Угрозы |
|--------|------|-------|--------|
| **PromptGuard 2** | Пользователь, недоверенные документы | Fine-tuned DeBERTa (BERT-семейство) | Прямые и косвенные jailbreak, универсальные инъекции |
| **AlignmentCheck** | Цепочка рассуждений агента (CoT) | Few-shot + семантический анализ через LLM | Захват цели, косвенные инъекции, рассогласование агента с задачей |
| **CodeShield** | Сгенерированный код | Semgrep + regex, 8 языков | Небезопасный код, опасные API, уязвимости |
| **Custom regex** | Любой | Детерминированные шаблоны | Пользовательские политики |

PromptGuard смотрит не только на финальный ответ, но и на **ход рассуждений** — «стеклянный ящик» вместо чёрного.

### Архитектура

SDK вокруг агентного цикла:

```python
firewall = LlamaFirewall(scanners={
    Role.USER: [ScannerType.PROMPT_GUARD],
    Role.ASSISTANT: [ScannerType.AGENT_ALIGNMENT],
})
result = firewall.scan(input_data)
```

Точки: до модели (ввод), во время рассуждений (ассистент), после генерации кода. **Не перехватывает tool_call напрямую** — это слой содержания, не авторизации действий.

### Детерминизм vs интеллект

| Компонент | Тип |
|-----------|-----|
| PromptGuard 2 | **Вероятностный** (нейросеть) |
| AlignmentCheck | **Интеллектуальный** (LLM-аудитор) |
| CodeShield | **Детерминированный** (статический анализ) |
| Regex | **Детерминированный** |

Известные слабости: многоязычные и Unicode-атаки, ложные срабатывания.

### Внешние сервисы

- **Together API** — для AlignmentCheck (`TOGETHER_API_KEY`).
- **PromptGuard** — локально (HuggingFace).
- **CodeShield / Semgrep** — локально.
- Используется в продакшене Meta.

# 7. Invariant (Guardrails + Gateway)

### Детекторы

Декларативный язык правил (Python-подобный) на **трассах** событий:

| Категория | Примеры правил |
|-----------|----------------|
| Запрет инструментов | `call is tool:delete_database` → raise |
| Порядок операций | `(output: get_website) -> (call: send_email)` запрещено |
| Потоки данных | данные из источника A не должны попадать в инструмент B |
| Встроенные предикаты | ПДн, секреты, небезопасный код, вредный контент |
| `prompt_injection(text, threshold=0.7)` | ML-классификатор внутри правила |
| LLM-as-Guardrail | Произвольная проверка через модель в тексте правила |
| Обнаружение циклов | Повторяющиеся вызовы инструментов |
| mcp-scan (отдельно) | Статический аудит MCP до деплоя |

Правило отделено от логики агента — безопасность может вести отдельная команда.

### Архитектура

**Два режима:**

1. **Gateway** — меняете base URL LLM и MCP → весь трафик через прокси Invariant; правила на каждый запрос до и после.
2. **Библиотека invariant-ai** — загрузка `LocalPolicy` и анализ массива сообщений в коде.

Модель событий: user/assistant/tool messages, tool calls, tool outputs — совместима с OpenAI chat format.

### Детерминизм vs интеллект

| Часть | Тип |
|-------|-----|
| Правила потоков, запреты инструментов | **Детерминированные** |
| `prompt_injection()` | **Вероятностный** |
| LLM-as-Guardrail | **Интеллектуальный** |
| mcp-scan | **Статический / детерминированный** |

### Внешние сервисы

- **Invariant Guardrails API** — опционально (`INVARIANT_API_KEY`, explorer.invariantlabs.ai).
- **LocalPolicy** — полностью offline.
- Gateway — self-hosted.

# 8. agent-airlock

### Детекторы

Шесть слоёв защиты в одном декораторе `@Airlock()`:

| Слой | Что делает |
|------|------------|
| Валидация | Удаление «призрачных» аргументов (придуманных моделью), строгая типизация Pydantic V2 |
| Политика | RBAC, лимиты вызовов, временные окна, capabilities (флаги возможностей) |
| ПДн | Маскирование 12 типов (включая индийские идентификаторы) |
| Файловая система | Обход каталогов, запрет чувствительных путей |
| Сеть | Блокировка исходящих к webhook'ам, контроль утечки |
| Песочница | E2B / Docker / локальный backend для опасного кода |
| Устойчивость | Автовыключатель, лимиты бюджета, отслеживание стоимости |
| Наблюдаемость | OpenTelemetry |

### Архитектура

**In-process декоратор** на функции-инструменты:

```python
@tool
@Airlock(mask_pii=True, policy=STRICT_POLICY)
def search_database(query: str): ...
```

Адаптеры: LangChain, LangGraph, CrewAI (`wrap_crew()`), OpenAI Agents SDK, PydanticAI, FastMCP, Anthropic. Правило: `@Airlock` **ближе к функции**, чем декораторы фреймворка.

«Вакцинация» — автоматическое оборачивание всех tools при старте.

### Детерминизм vs интеллект

**Почти полностью детерминированный.** Нет ML-детектора инъекций. PII — шаблоны и NER-подобная логика, не большая языковая модель.

### Внешние сервисы

- **E2B Cloud** — опционально для песочницы (~125 мс холодный старт).
- **OpenTelemetry** — экспорт в ваш стек наблюдаемости.
- Без E2B — локальный Docker или ограниченный локальный режим.

# 9. Aegis

### Детекторы

Трёхступенчатый конвейер на каждый tool_call:

| Стадия | Проверки |
|--------|----------|
| 1. Извлечение | Глубокий разбор всех строк в аргументах |
| 2. Сканирование содержимого | SQL-инъекции (DROP, DELETE, TRUNCATE), обход путей, инъекции в shell, шаблоны «игнорируй инструкции», утечка на внешние URL, ПДн |
| 3. Политика | YAML/композируемые правила, режимы: сразу блок / ожидание человека |
| Аномалии (опционально) | 9 измерений поведения после ~200 трасс: новый инструмент, всплеск частоты, дрейф формы аргументов |

Журнал: Ed25519 + SHA-256 цепочка хешей — изменение записи ломает цепь.

### Архитектура

Три способа подключения:

1. **SDK** — `agentguard.auto("http://localhost:8080")` патчит 14 фреймворков (Python/JS/Go), код агента не меняется.
2. **HTTP/MCP-прокси** — для закрытых бинарников агентов.
3. **Compliance Cockpit** — веб-панель: очередь одобрений, kill switch, экспорт PDF/CSV, алерты.

```
Агент → SDK перехватывает → Gateway :8080 → allow/block/pending → Dashboard :3000
```

### Детерминизм vs интеллект

| Часть | Тип |
|-------|-----|
| Шаблоны SQL/shell/инъекций | **Детерминированные** |
| ПДн | **Детерминированные** |
| Аномалии поведения | **Статистический / обучающийся** — не формальная гарантия |

По заявленным тестам: 48/48 атак заблокированы до исполнения; ложноположительные ~1,2% на 500 легитимных вызовов; задержка ~8,3 мс (медиана).

### Внешние сервисы

# 17. CaMeL (Google DeepMind)

### «Детекторы»

Не детекторы в классическом смысле — **движок меток и политик**:

| Механизм | Суть |
|----------|------|
| Capabilities на каждое значение | Кто может читать, откуда данные (доверенные / недоверенные) |
| IFC-алгебра | Операции над данными наследуют метки |
| Policy engine | Перед каждым tool_call — проверка меток аргументов |
| P-LLM | Планирует, **не видит** сырой недоверенный текст |
| Q-LLM | Извлекает структуры из недоверенного текста, **без инструментов** |
| Custom Python interpreter | Выполняет план, строит граф потоков данных |

Пример: email из письма атакующего помечен `untrusted` → `send_email` с таким получателем **блокируется** политикой, даже если P-LLM «согласился».

### Архитектура

Полная перестройка пайплайна агента:

```
Запрос → P-LLM (план на Python) → Interpreter (метки + политика) → Q-LLM (извлечение) → tool calls
```

Исследовательский артефакт (GitHub google-research/camel-prompt-injection), **не продукт Google**.

### Детерминизм vs интеллект

| Часть | Тип |
|-------|-----|
| Проверка меток и политик | **Детерминированная** (доказуемая безопасность в рамках модели угроз) |
| Планирование P-LLM, извлечение Q-LLM | **Интеллектуальное** |

AgentDojo: 77% задач с доказуемой безопасностью vs 84% без защиты (~7% потери полезности).

### Внешние сервисы

API языковых моделей (Claude, GPT и др.). Локального «без модели» режима нет.
