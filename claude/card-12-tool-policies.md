# Карточка №12 — Политики на tools (YAML / Rego / Cedar)

> Статус: **полная**. Слой: Действие. Класс: **превентивный**.
> Несущее поле: **§4+§6**. Ось §4 пинится: OWASP Agentic Top 10 **2026** / LLM Top 10 **2025**.
> Якорь: OPA Rego / Cedar `[док]`; Progent arXiv:2504.11703 **v3** `[проверено 2026-07-07]`; AGT GovernancePolicy `[док]`.

---

## 1. Идентификация и декомпозиция

Декларативные **policy engines** на границе tool-call: allow/deny/require_approval по имени tool, аргументам, контексту сессии. Семейства:

- **YAML/JSON политики** — allow/deny/require_approval на tool (AGT, agentguard, Aegis, defenseclaw).
- **OPA Rego / Cedar** — enterprise-декларативные политики (AGT, defenseclaw).
- **Progent DSL** — JSON/JSON Schema привилегий + fallback + динамические обновления; **SMT-солвер** на каждое обновление политики.
- **Invariant trace rules** — «после get_website нельзя send_email» (дедуп: Invariant = Snyk = AgentDojo — одна линия).

**Развязка CEL:** CEL-выражения на MCP tool по JWT claims — точка врезки **gateway (№24)**, не in-process policy engine. В №12 — политики **на tool-call**; в №24 — **на входе в gateway**.

**Развязка с №14/№16/№20:** №14 — default-deny подложка; №16 — IFC по меткам данных; №20 — валидация формы аргументов. №12 — **смысловые правила** на допустимость вызова.

## 2. Статус после Этапа 0
**Подтверждён** (превентивный). Progent SMT — **восстановлен** после коррекции Stage 0 D1 (v3, не v1).

## 3. Точка врезки и режим
**pre-tool-call** × **inline-блокировка** (или require_approval / pending). Политика оценивается на каждом вызове до исполнителя.

## 4. Модель угроз

**Закрывает:**
- **ASI02 Tool Misuse** — блок деструктивных/неавторизованных вызовов по правилам.
- **ASI03 Identity & Privilege Abuse** — confused deputy при корректной политике субъекта.
- Частично **LLM06 Excessive Agency** — ограничение набора допустимых действий.

**НЕ закрывает:**
- **Ошибку/дыру в политике** — гарантия ровно настолько сильна, насколько полно описаны правила.
- **Потоки данных** без явных flow-правил — для пообъектных меток см. №16; для статики графа — №28.
- **Семантически валидный злоупотребление** в рамках allow.
- **Prompt injection** как текстовая атака — политика на tool, не на ввод.

## 5. Обходы и слепые зоны

- **Неполная онтология tools** — новый tool без правила = дыра (особенно без №14).
- **Expansion без контроля** — Progent решает через SMT: expansion требует одобрения; без SMT-дисциплины политика раздувается.
- **Обход через разрешённый tool** — политика на имя tool, не на побочный эффект.
- **Рассинхрон политики и реальности** — policy drift при быстром добавлении MCP tools.

## 6. Цена эксплуатации — несущее поле (enterprise-якорь)

- **Владелец правил** — security/platform команда; политики живая сущность, не «настроил раз».
- **Латентность** — OPA/Cedar/Progent на каждый tool_call; Progent SMT добавляет оверхед на **обновления** политики, не на каждый вызов.
- **Утилити-налог** — ложные блокировки при грубых правилах; Progent: **6%** обновлений политики потребовали одобрения на AgentDojo `[проверено 2026-07-07, arXiv:2504.11703 v3]`.
- **Monotonic confinement** — narrowing применяется авто, expansion — только с одобрением; доказательство в §6 статьи v3.

## 8. Сочетаемость

- **Требует №14 (default-deny)** как замыкание.
- **Комплемент №16** — политики на tool vs IFC на данных; Invariant rules — грубый предок flow-ограничений.
- **Партнёр №28** — статический toxic flow до рантайма.
- **Не дублировать №20** — schema аргументов vs policy смысла.

## 9. Проверочный протокол

- **Каноничная атака:** вызов `delete_database` или `send_email` с exfil-аргументом при политике deny → блок до исполнения.
- **Обход:** действие через tool с allow, но вредоносный side-effect → проходит; зафиксировать границу.
- **Progent-специфика:** попытка expansion политики без одобрения → SMT reject.
- **Статус:** `[не выполнено]` → experiments-todo.

## 11. Сценический тезис

> «Политики на tools — это то, как security-команда говорит агенту „ты можешь только это“. Progent v3 добавил редкую вещь: математическое обещание, что права без одобрения только сужаются — SMT-солвер на каждое обновление, и лишь 6% изменений потребовали человека на AgentDojo. Но политика с дырой — это дырявая политика, какой бы солвер ни стоял за кулисами.»

## 12. Кандидат в демо/пример

**Есть.** Два кадра: (1) policy deny на `send_email` после `read_untrusted_web` (Invariant rule); (2) Progent narrowing vs expansion — авто-сужение проходит, расширение без approve — блок SMT.
