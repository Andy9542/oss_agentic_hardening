# Проверка аргументов по JSON-схеме и строгим типам

## Определение

Перед выполнением инструмента каждый **аргумент** вызова проверяется по **схеме**: допустимые типы (`string`, `integer`, не `number` с дробью), перечисления (`enum`), регулярные выражения для строк, минимум/максимум, обязательные поля. Поля, **не описанные в схеме** («призрачные аргументы» от модели), **отбрасываются**.

## Как это работает пошагово

1. Модель возвращает: `вызвать search_db(query="...", admin=true)`.
2. **Валидатор** сверяет JSON с контрактом инструмента.
3. `admin` нет в схеме → **удаляется** (ghost argument).
4. `query` должен быть строкой, не объектом → иначе **отказ**.
5. При `additionalProperties: false` любое лишнее поле → **блок всего вызова**.
6. Только после успеха — исполнение.

## От чего защищает

- **Инъекция через лишние поля**, которые сервер бэкенда может неожиданно обработать.
- **Путаница типов** (число вместо строки → обход экранирования).
- Выход за **enum** (только `read` | `write`, модель передала `delete`).
- Частично — инъекции в path-полях при жёстком `pattern`.

## От чего НЕ защищает

- Легитимное поле `query` со значением `DROP TABLE users`.
- Слишком **широкая** схема (`object` без ограничений).
- Инструменты без формального контракта.

## Алгоритмы и механизмы (подробно)

### JSON Schema (черновик 07+)

Стандарт OpenAI function calling и MCP: `type`, `properties`, `required`, `pattern`, `format: uri`.

### Pydantic V2 strict (agent-airlock)

Python-модели с запретом неявного приведения типов; несоответствие → исключение до вызова функции.

### Удаление призрачных аргументов

Модель часто «додумывает» параметры из описания API. Стриппинг неизвестных ключей — простая и эффективная мера.

### Технические детали внедрения

- **Канонизация перед валидацией.** Аргументы полезно приводить к предсказуемому виду до проверки: нормализовать пути, обрезать управляющие символы, раскодировать JSON-строки, унифицировать представление булевых и числовых значений. Иначе один и тот же смысл проходит по разным веткам валидации.
- **Жёсткая модель типов.** Безопасный режим запрещает неявные преобразования вроде `"1" -> 1` или `1 -> true`. Это особенно важно для флагов доступа, временных интервалов и лимитов, где приведение типов может менять семантику действия.
- **Вложенные структуры и union-типы.** Реальные инструменты принимают массивы, словари и объекты в объектах. Схема должна описывать глубину вложенности, ограничения на длину массивов, уникальность элементов и допустимые комбинации полей.
- **Unknown fields policy.** Нужно явно выбрать стратегию: `strip` убирает лишние поля и повышает совместимость, `hard-fail` жёстче и лучше для критичных операций. Обычно для read-only tools допускают мягкий режим, а для write/delete - только отказ.
- **Форматы и инварианты.** Помимо `pattern` и `enum`, стоит проверять `format` (`uri`, `email`, `date-time`) и кросс-полевые ограничения: например, `start <= end`, `mode=delete` требует `approval_token`, путь должен лежать внутри рабочей директории.
- **Версионирование контрактов.** Если схема клиента и бэкенда расходится, валидатор либо начнёт резать легитимные поля, либо пропускать устаревшие. Поэтому схемы полезно версионировать и проверять на совместимость при деплое.
