# Статическая проверка навыков и плагинов

## Определение

**До запуска** (или при установке) файлы навыков, плагинов и конфигов агента анализируются **без исполнения**: сигнатуры YARA, разбор markdown, поиск скрытых инструкций, опционально — вторая модель как «судья» семантики.

Это **shift-left** контроль: ловит вредоносный артефакт до того, как агент получит к нему доступ в рантайме.

## Как это работает пошагово

1. **Обход файлов** — каталоги skills/, `.cursor/`, манифесты MCP, plugin.json.
2. **YARA / pattern matcher** — совпадение с сигнатурами malware, `curl|bash`, base64-блоки, jailbreak-фразы (aguara: 193 YAML-правила).
3. **NLP / markdown AST** — инструкции в HTML-комментариях, невидимых секциях, «доверься мне» + eval.
4. **Toxic flow (статика)** — в одном конфиге есть read_secrets и http_post (snyk, aguara).
5. **LLM-судья** (defenseclaw, опционально) — семантика: «это приказ игнорировать политику?»
6. **Вердикт** — разрешить / карантин / блок; без способа №31 остаётся только отчёт в CI.

## От чего защищает

- Инъекции и скрытые инструкции **внутри навыка** до первого вызова.
- Вредоносные паттерны в markdown и описаниях MCP (E001, E004 в snyk/agent-scan).
- Захардкоженные секреты в файлах навыка (пересечение с LLM02).
- Отравление **статического** контекста, который попадёт в память агента (ASI06).

## От чего НЕ защищает

- Вредоносное поведение, проявляющееся **только** в рантайме (динамическая загрузка, rug-pull после baseline).
- Обфускация без сигнатуры и без срабатывания NLP.
- Бинарники и артефакты вне пути сканирования.
- Легитимный навык с **уже одобренным** вредоносным описанием в первом baseline (нужен способ №25).

## Алгоритмы и механизмы (подробно)

| Движок | Примеры | Детерминизм |
|--------|---------|-------------|
| Aho-Corasick + regex (aguara) | curl\|bash, hardcoded keys | Да |
| Goldmark AST (aguara) | скрытые HTML-комментарии | Да |
| YARA (defenseclaw) | malware families | Да |
| LLM judge (defenseclaw) | семантика промпта в skill | Нет |
| Toxic flow graph | read + exfil в одном конфиге | Да |

### Технические детали внедрения

- **Многослойный разбор форматов.** Один и тот же навык может содержать Markdown, YAML frontmatter, JSON-манифест, embedded shell и ссылки на удалённые ресурсы. Сканер должен разбирать формат послойно, а не искать строки по сырому тексту.
- **AST и скрытые области.** Для markdown полезно строить AST, отдельно анализировать HTML-комментарии, code fences, ссылки, изображения и raw-блоки. Вредоносные инструкции часто прячут именно в «невидимых» пользователю местах.
- **YARA как быстрый фильтр.** Сигнатуры хорошо подходят для base64-обфускации, downloader-паттернов, ключевых фраз jailbreak и характерных конструкций вредоносных скриптов. Но правила нужно версионировать и снабжать suppression-механизмом, иначе они быстро начинают шуметь.
- **Семантический анализ по требованию.** Дорогой LLM- или NLP-анализ выгодно запускать только на фрагментах, которые уже пометили дешёвые фильтры. Это снижает стоимость и уменьшает поверхность доверия к внешней модели.
- **Граф опасных потоков.** Кроме текста, полезно извлекать declared capabilities: чтение файлов, сеть, shell, доступ к кошельку, отправку webhook. Затем строить toxic-flow правила вроде `read secret + external POST`.
- **Границы метода.** Статика почти не видит поведение бинарных артефактов, динамически загружаемого кода и удалённых зависимостей. Поэтому её стоит сочетать с admission-политиками и runtime-enforcement.
